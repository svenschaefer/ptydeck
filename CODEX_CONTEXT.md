## Architecture Baselines To Preserve

- Frontend runtime no longer uses the old stream-scanning/plugin/notification path for normal activity handling; keep raw terminal streaming plus visible-output-based active/inactive detection only.
- Command surface model is intentionally consistent: `>` for quick switching, `@<sessionSelector>` for explicit direct-target slash routing, and `/` for the slash-command plane.
- Session notes are persisted and multiline; the session header shows a first-line preview with truncation and tooltip access to the full note.
- Quick-ID swap ordering is backend-persisted and shared across reload, reconnect, and restart restore.
- Send safety is configured through explicit per-session `inputSafetyProfile` option fields, not presets.
- Send safety is also intentionally not a monolithic "strict mode". The baseline now exposes one explicit catch-all guard (`confirmOnAnyInput`) for operators who want every non-empty send to require confirmation; the remaining send-safety toggles are narrower structural, heuristic, pattern-based, or threshold-based checks and should keep being labeled that way in the UI and slash/help surfaces.
- Terminal-local paste now also has an explicit follow-up model instead of a fire-and-forget assumption: each paste can be observed against subsequent raw session output for full echo, partial echo, placeholder acknowledgement, or stalled states, `Continue Paste` must reuse the session's configured send terminator, and optional `autoContinueStalledPaste` remains limited to bounded terminal-local paste heuristics rather than generic automatic send retries.
- Session settings are tabbed; terminal-surface `Ctrl-C` ambiguity is resolved through a local copy-versus-cancel prompt.
- Remote session baseline exists for `local` and `ssh`, including remote auth metadata, SSH host-key trust persistence, backend SSH host-key probing, reconnect metadata, and saved connection profiles.
- Read-only sharing exists for session/deck spectator access.
- The multi-device terminal-control requirement baseline is now fixed at the document level in `docs/Multi-Device Terminal Control Requirements.md`: each session has exactly one Owner, zero or one Controller, and zero or more Spectators; control is single-writer and deterministic; PTY resize authority belongs only to the active Controller or a stable host default when no Controller exists; globally synchronized runtime state is intentionally narrower than client-local layout/focus/search state; and controller/observer metadata must remain visible to attached clients.

- Terminal-app identification should be implemented as a shared runtime capability, not as messaging-only logic. The normalized identity contract should expose at least `family`, `label`, `source`, `confidence`, `details`, and `updatedAt`, and must tolerate low-confidence or unknown states rather than forcing a guess.
- App-identity signal priority should be: explicit launch/session hints first, local foreground-process inspection second, shell-integration markers third, bounded terminal-mode signals fourth, and output heuristics last. The system should prefer stronger runtime signals over regex guesses whenever both are available.

If the foreground owner resolves only to a shell wrapper, `tmux`, `screen`, or another multiplexer, the confidence model should degrade instead of pretending the wrapped app is known.
